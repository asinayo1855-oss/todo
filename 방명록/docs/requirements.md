# 방명록 요구사항 문서

## 1. 개요

누구나 이름 또는 별명으로 글을 남길 수 있는 방명록 웹앱. 글 작성 시 비밀번호를 설정하여
작성자 본인이 나중에 수정·삭제할 수 있고, 다른 사람은 각 글에 답글을 달 수 있다.
답글에도 동일하게 비밀번호를 설정해 작성자가 수정·삭제할 수 있다.

- **형태**: Todo 앱과 완전히 분리된 별도 프로젝트 (`방명록/` 폴더, 별도 배포)
- **사용 범위**: 불특정 다수, 로그인/회원가입 없음 (누구나 이름·별명만 입력하고 작성)
- **데이터 저장**: Supabase Postgres, 클라이언트에서 anon key로 직접 접근 (서버 없음)
- **참고**: 로그인이 없고 클라이언트가 DB에 직접 접근하는 구조이므로, 아래 명시된 것 이상의
  완전한 보안(예: 완벽한 위·변조 방지)은 이 아키텍처의 근본적인 한계로 다루지 않는다.

## 2. 핵심 기능

### 2.1 글(방명록 항목) 작성
- 이름 또는 별명 (필수)
- 내용 (필수)
- 비밀번호 (필수, 수정·삭제 시 사용)
- 작성 시각 자동 기록

### 2.2 글 목록 조회
- 최신순으로 목록 표시
- 작성자 이름/별명, 내용, 작성 시각 노출 (비밀번호는 절대 노출 안 됨)

### 2.3 글 수정
- 목록에서 "수정" 클릭 → 비밀번호 입력 요구
- 비밀번호 검증 통과 시에만 이름/내용 수정 가능

### 2.4 글 삭제
- 목록에서 "삭제" 클릭 → 비밀번호 입력 요구
- 비밀번호 검증 통과 시에만 삭제 (하위 답글도 함께 삭제)

### 2.5 답글 작성
- 각 글 아래에 답글 작성 가능
- 답글도 이름/별명, 내용, 비밀번호를 동일하게 입력
- **답글 구조는 1단계만 허용** — 답글에는 추가 답글을 달 수 없음 (원글에만 답글 가능)

### 2.6 답글 수정 · 삭제
- 글과 동일하게 비밀번호 검증 후 수정·삭제 가능

### 2.7 관리자 기능
- 운영자는 마스터 비밀번호로 로그인해 관리자 모드 진입
- 관리자 모드에서는 각 글/답글 작성자 비밀번호를 몰라도 삭제 가능 (수정은 불가, 삭제만)
- 관리자 로그인 상태는 세션 단위로 유지 (브라우저 탭/세션 종료 시 해제)

## 3. 비밀번호 처리 방식

- 작성 시 비밀번호를 **클라이언트에서 해시**(bcrypt.js 등, salt 포함)한 값만 DB에 저장한다.
  평문 비밀번호는 어떤 경우에도 DB에 저장하거나 네트워크로 그대로 전송하지 않는다.
- 수정·삭제 시 입력한 비밀번호를 같은 방식으로 해시하여 DB에 저장된 해시와 비교한다.
- 한계: 클라이언트 코드(해시 로직, Supabase anon key)가 브라우저에 그대로 노출되므로,
  DB를 직접 조작할 수 있는 사람에게는 완전한 보안이 아니다. "가벼운 무단 수정·삭제 방지"
  수준의 보호로 이해하고 사용한다. 관리자 마스터 비밀번호도 동일한 한계를 가진다.

## 4. 데이터 모델 (초안)

### `entries` (방명록 글)
| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | uuid (PK) | |
| author_name | text | 이름/별명 |
| content | text | 내용 |
| password_hash | text | 클라이언트 해시 결과 |
| created_at | timestamptz | 작성 시각 |
| updated_at | timestamptz | 수정 시각 (수정 없으면 null) |

### `replies` (답글)
| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | uuid (PK) | |
| entry_id | uuid (FK → entries.id) | 어느 글에 대한 답글인지 |
| author_name | text | 이름/별명 |
| content | text | 내용 |
| password_hash | text | 클라이언트 해시 결과 |
| created_at | timestamptz | 작성 시각 |
| updated_at | timestamptz | 수정 시각 |

- `entries` 삭제 시 관련 `replies`도 함께 삭제 (`ON DELETE CASCADE`)
- 답글에는 상위 답글 참조 컬럼을 두지 않는다 (1단계 구조 확정)

## 5. 화면 구성 (초안)

- **메인 페이지**: 글쓰기 폼 (상단) + 방명록 목록 (하단, 각 글 아래 답글 목록과 답글 작성 폼 포함)
- 글/답글의 "수정", "삭제" 버튼 클릭 시 비밀번호 입력 모달(또는 인라인 입력) 표시
- 관리자 모드 진입 UI (예: 하단의 "관리자 로그인" 링크 → 마스터 비밀번호 입력)
- 관리자 모드에서는 각 글/답글에 비밀번호 없이 바로 "삭제" 가능한 버튼 노출

## 6. 비기능 요구사항

- 반응형 레이아웃 (모바일/데스크톱)
- Supabase RLS 활성화, anon 권한으로 INSERT/SELECT/UPDATE/DELETE 허용하되
  UPDATE/DELETE는 애플리케이션 레벨(비밀번호 검증)에서 통제
  — RLS 정책 자체로 비밀번호를 검증할 수는 없으므로, 실제 검증은 클라이언트 로직에 의존함을 인지

## 7. 이번 범위에서 제외

다음은 이번 요구사항에 포함하지 않는다. 필요 시 추후 별도로 논의한다.
- 글자 수 제한, 작성 빈도(도배 방지) 제한
- 캡차 등 봇/스팸 방지 장치
- 페이지네이션/무한 스크롤
- 신고 기능, 욕설/비속어 필터
